## 3. Формат, поля, признаки и структура разметки (Labels & Schema)

### 3.1. Структура входных алертов Wazuh (`*_wazuh.json`, формат JSON Lines)
Каждая строка файла представляет собой валидный JSON-объект срабатывания Wazuh со следующими ключевыми полями:
- `@timestamp` *(string, ISO-8601)* $\rightarrow$ конвертируется в `ts` *(float, Unix epoch)* для хронологической сортировки и расчёта скользящих окон;
- `predecoder.hostname` и `agent.name` *(string)* $\rightarrow$ имя хоста-источника (`mail`, `intranet-server`, `wazuh-client`);
- `agent.ip` *(string)* $\rightarrow$ IP-адрес агента SIEM;
- `location` *(string)* $\rightarrow$ путь к лог-файлу или сервису (`/var/log/apache2/intranet-access.log`, `/var/log/auth.log`, `/var/log/suricata/eve.json`, `/var/log/mail.log`). **Критически важное поле:** используется в нашей Location-Aware CMDB для точного определения атакуемого сервиса, когда `predecoder.hostname` отсутствует;
- `rule.id` *(string)* $\rightarrow$ идентификатор правила Wazuh (например, `31101`, `31151`, `5402`, `5304`, `9701`, `20101`);
- `rule.level` *(int, 0..15)* $\rightarrow$ штатный уровень критичности Wazuh (**используется как `f_severity` и как Baseline №1**);
- `rule.groups` *(array of strings)* $\rightarrow$ категориальные теги правила (`["web", "accesslog", "attack"]`, `["syslog", "sudo"]`, `["dovecot", "authentication_success"]`), служащие входом для нашего мэппера тактик MITRE ATT&CK;
- `rule.description` и `full_log` *(string)* $\rightarrow$ текстовое описание правила и сырая строка лога.

### 3.2. Структура Ground-Truth разметки (`labels.csv`)
Файл `03_dataset/labels.csv` содержит **80 размеченных интервалов** (8 сценариев $\times$ 10 стадий атаки) со столбцами `scenario, attack, start, end` (Unix timestamps):
1. `network_scans` (Reconnaissance — сетевое сканирование `nmap`)
2. `service_scans` (Reconnaissance — сканирование сервисов)
3. `dirb` (Reconnaissance — перебор директорий веб-сервера)
4. `wpscan` (Reconnaissance — сканирование уязвимостей WordPress)
5. `webshell` (Initial Access / Exploitation — загрузка веб-шелла через уязвимость плагина wpDiscuz **CVE-2020-24186**)
6. `cracking` (Credential Access — перебор паролей)
7. `reverse_shell` (Execution — открытие обратной оболочки с веб-сервера)
8. `privilege_escalation` (Privilege Escalation — переход `www-data -> jhall` через `su` и выполнение `sudo` до `root`)
9. `service_stop` (Impact — остановка системного сервиса)
10. `dnsteal` (Exfiltration — скрытая эксфильтрация данных через DNS-туннель)

> **Строгое правило отсутствия утечки целевой переменной (Zero Label Leakage):** файл `labels.csv` **НИКОГДА** не подаётся на вход алгоритму скоринга `scoring.py` — он используется исключительно в `evaluate.py` для проверки качества ранжирования! Сам модуль ESPM определяет предполагаемую фазу атаки исключительно по открытым полям алерта Wazuh (`rule.groups` и `rule.description`).

## 4. Очистка, предобработка и конструирование признаков (Feature Engineering)

В ходе проверки датасета вручную и программно выявлены и решены 3 особенности данных:
1. **Устойчивый потоковый парсинг и фильтрация таймстемпов:** единичные повреждённые JSON-строки или записи без валидного `@timestamp` безопасно отбрасываются в `parse_wazuh_jsonl` (проверено модульными тестами в `test_espm.py`).
2. **Хронологическое упорядочивание:** поскольку логи разных сервисов (`apache2`, `suricata`, `syslog`) сбрасываются в файл с небольшим рассинхроном буферизации, перед подачей в потоковый скорер алерты каждого сценария сортируются по возрастанию `alert.ts`.
3. **Обогащение контекстом активов (Location-Aware CMDB):** так как в AIT-ADS нет отдельного файла CMDB, нами сконструирована детерминированная таблица активов на основе документации тестового стенда AIT-LDS v2 и пары `(alert.host, alert.location)`:
   - `intranet-server` (`/var/log/apache2/intranet*`, `host=intranet*`, `/var/log/audit*`): целевой корпоративный портал с CVE-2020-24186 (`criticality = 0.95, vulnerability = 0.90, centrality = 0.85`);
   - `mail-server` (`/var/log/mail*`, `host=*mail*`): почтовый сервер Dovecot/Postfix (`criticality = 0.55..0.90, vulnerability = 0.30..0.60, centrality = 0.50..0.80`);
   - `network-ids-sensor` (`/var/log/suricata/*`): пассивный сетевой сенсор, генерирующий фоновые TLS-уведомления (`criticality = 0.35, vulnerability = 0.20, centrality = 0.50`);
   - `client` / `external`: рядовые рабочие станции и внешние узлы (`criticality = 0.10..0.30`).

## 5. Разделение на выборки (Train / Dev / Held-out Test Split)

Поскольку события внутри одного сценария связаны единой временной цепочкой атаки, случайное перемешивание алертов (random split) внутри одного сценария привело бы к **утечке данных во времени (temporal data leakage)**. Поэтому применяется **групповое стратифицированное разбиение по независимым сценариям (Scenario-Level Group Split)**:
- **Train / Calibration Set (4 сценария, 745 779 алертов):** `fox`, `santos`, `shaw`, `wardbeck` — используются для анализа распределений правил, отладки CMDB-мэппинга и настройки весов $w_i$.
- **Held-out Test Set (2 сценария, 666 791 алерт):** `russellmitchell` (умеренный баланс 20.6% атак) и `wilson` (высокая нагрузка 69.1% атак) — отложенная выборка для честной итоговой проверки гипотез H1 и H2.
- **Reserve Validation Set ко 2-й предзащите (2 сценария, ~881 000 алертов):** `harrison` и `wheeler`.

## 6. Хранение и передача данных между компонентами

1. **Входной контур:** сырые оповещения хранятся в формате JSONL (`*_wazuh.json` либо живой лог `/var/ossec/logs/alerts/alerts.json` на сервере Wazuh Manager) и читаются построчно итератором без загрузки всего файла в DOM.
2. **Внутреннее состояние в памяти (In-Memory State):** для каждого канонического актива хранятся только:
   - кольцевая очередь `deque` секундных корзин за последние `600 с` (не более 600 элементов на хост);
   - словарь активных стадий атаки `_stage_memory` за последние `3600 с` (не более 11 ключей на хост).
   Объём потребляемой оперативной памяти состояния составляет **менее 1 МБ** даже при обработке миллионов алертов.
3. **Выходной контур:** приоритизированные инциденты и их объяснения сериализуются в структурированный JSON (`results.json`, `explanation_example.json`) и отображаются в веб-интерфейсе `dashboard.html`.

## 7. Резервные варианты датасета (Backup Datasets)

1. **Резервный датасет №1 — AIT Log Data Set v2.1 (AIT-LDS v2.1, Zenodo DOI `10.5281/zenodo.19483937`):** сырые системные и веб-логи тех же 8 инфраструктур до обработки SIEM. Позволяет при необходимости воспроизвести генерацию алертов на собственной версии Wazuh Manager.
2. **Резервный датасет №2 — Собственный лабораторный Docker-стенд Wazuh (план на февраль 2027):** контейнер Wazuh Manager + уязвимый контейнер WordPress/Linux, на котором скриптом воспроизводится цепочка `nmap -> wpscan -> exploit -> su -> sudo` для live-демонстрации на финальной защите.
